## Goal
Find out *why* a Node service is slow or growing in memory using real measurements — not guesses.

## Background

### Measure first
Performance work starts with a reproducible load test and a metric (requests/sec, p99 latency, memory after N requests). Change one thing, measure again. Tools:

| Question | Tool |
|----------|------|
| How fast is it under load? | `autocannon`, `k6`, `wrk` |
| Where is CPU time spent? | `node --cpu-prof` → `.cpuprofile` → Chrome DevTools / speedscope; `node --prof` |
| Is the event loop blocked? | `perf_hooks.monitorEventLoopDelay`, `performance.eventLoopUtilization()` |
| What's using memory? | `process.memoryUsage()`, heap snapshots (`--heapsnapshot-signal`, `v8.writeHeapSnapshot()`), DevTools Memory tab |
| Is GC thrashing? | `--trace-gc`, `PerformanceObserver` for `'gc'` entries |
| Time a code section | `performance.mark` / `measure`, `performance.timerify` |

### Reading a CPU profile
A **flame graph** shows call stacks over time: width = time spent. Look for wide bars in **your** code (sync crypto, JSON, regex, loops) rather than in Node internals. "Self time" is time in the function itself; "total time" includes everything it calls.

### Memory: heap, RSS, and leaks
- `heapUsed` — live JS objects. `heapTotal` — heap reserved by V8. `rss` — total process memory (heap + Buffers + code + native). `external`/`arrayBuffers` — memory for Buffers outside the heap.
- Memory going **up and down** is normal (garbage collection). A **leak** is memory that keeps growing across GCs under steady load.
- Classic Node leaks: unbounded caches/Maps, listeners added per request and never removed, closures retaining large objects, timers never cleared, global arrays of requests/sockets.

### Finding a leak with heap snapshots
Take a snapshot, run load, take another, and use DevTools' **Comparison** view: sort by "# Delta" or "Size Delta" to see which object types grew, then follow the **retainers** chain to the code holding them.

### Event loop utilisation (ELU)
`performance.eventLoopUtilization()` reports the fraction of time the loop was busy. ELU near 1.0 means the process is CPU-saturated — adding more concurrency won't help; you need less work per request, workers, or more processes.

### 1. A deliberately slow server

mkdir a6-4-profiling && cd a6-4-profiling

```js
// slow.js
import { createServer } from 'node:http';
import { pbkdf2Sync, randomBytes } from 'node:crypto';

const users = Array.from({ length: 5000 }, (_, i) => ({ id: i, name: `user${i}`, email: `u${i}@x.com`, tags: ['a', 'b', 'c'] }));

function slowStringify(obj) { return JSON.stringify(JSON.parse(JSON.stringify(obj))); }   // pointless double work

createServer((req, res) => {
  if (req.url === '/users') {
    const body = slowStringify(users.filter(u => /^user\d*7$/.test(u.name)));
    return res.end(body);
  }
  if (req.url === '/login') {
    pbkdf2Sync('password', randomBytes(16), 100_000, 64, 'sha512');   // sync KDF blocks the loop
    return res.end('ok');
  }
  res.end('hello');
}).listen(3000);

// --cpu-prof only writes its file on a normal exit, so turn Ctrl+C / kill -INT into one
process.on('SIGINT', () => process.exit(0));
```

### 4. Measure event loop health from inside

```js
// health.js — import this at the top of slow.js
import { monitorEventLoopDelay, performance } from 'node:perf_hooks';

const delay = monitorEventLoopDelay({ resolution: 20 });
delay.enable();
let lastELU = performance.eventLoopUtilization();

setInterval(() => {
  const elu = performance.eventLoopUtilization(lastELU);
  lastELU = performance.eventLoopUtilization();
  const mem = process.memoryUsage();
  console.log(
    `ELU ${(elu.utilization * 100).toFixed(0)}% | loop p99 ${(delay.percentile(99) / 1e6).toFixed(1)}ms` +
    ` | heap ${(mem.heapUsed / 1e6).toFixed(1)}MB rss ${(mem.rss / 1e6).toFixed(1)}MB`,
  );
  delay.reset();
}, 2000).unref();
```

Watch ELU hit ~100% and loop p99 spike while `/login` is under load (before the fix), then stay low after.

### 5. Time sections with performance marks

```js
// marks.js
import { performance, PerformanceObserver } from 'node:perf_hooks';

new PerformanceObserver((list) => {
  for (const e of list.getEntries()) console.log(`${e.name}: ${e.duration.toFixed(2)}ms`);
}).observe({ entryTypes: ['measure', 'function'] });

const data = Array.from({ length: 200_000 }, (_, i) => ({ i, v: Math.random() }));

performance.mark('sort-start');
data.slice().sort((a, b) => a.v - b.v);
performance.mark('sort-end');
performance.measure('sort 200k objects', 'sort-start', 'sort-end');

const timedStringify = performance.timerify(function stringifyAll() { return JSON.stringify(data); });
timedStringify();
```

### 6. Create, observe, and fix a memory leak

```js
// leak.js
import { createServer } from 'node:http';
import { EventEmitter } from 'node:events';
import { writeHeapSnapshot } from 'node:v8';

const events = new EventEmitter();
events.setMaxListeners(0);                // hides the warning that would have told us
const requestLog = [];                    // leak #1: grows forever

createServer((req, res) => {
  const payload = Buffer.alloc(10_000);   // ~10 KB per request
  requestLog.push({ url: req.url, at: Date.now(), payload });
  events.on('config-change', () => payload.length);   // leak #2: listener per request, retains payload
  res.end('ok');
}).listen(3000);

process.on('SIGUSR2', () => console.log('snapshot written:', writeHeapSnapshot()));
setInterval(() => console.log(`heapUsed ${(process.memoryUsage().heapUsed / 1e6).toFixed(1)}MB`), 2000).unref();
```

```bash
node leak.js &
kill -USR2 %1                                   # snapshot 1
npx autocannon -c 20 -d 20 localhost:3000
kill -USR2 %1                                   # snapshot 2
```

Load both `.heapsnapshot` files in Chrome DevTools → Memory. Use **Comparison** to find the growth (`Buffer`/`ArrayBuffer`, closures, the `requestLog` array), and follow retainers back to `requestLog` and the `config-change` listeners. Fix both leaks (a bounded ring buffer for the log; no per-request listeners), and confirm heap stays flat under a second 20-second load test.

### 7. Watch the garbage collector

```bash
node --trace-gc leak.js 2>&1 | head -30
```

Note the difference between frequent cheap **Scavenge** (young generation) and rarer expensive **Mark-Compact** (old generation) collections.
