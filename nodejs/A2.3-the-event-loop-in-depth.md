## Goal
Predict exactly when any callback will run, and recognise the patterns that block or starve the event loop.

## Background

### What the event loop does
After Node runs your entry script to completion, it enters the event loop: a loop that keeps checking for work (expired timers, completed I/O, `setImmediate` callbacks) and runs the corresponding callbacks. When there is nothing left that could ever produce a callback — no timers, sockets, servers, or pending operations — the loop exits and so does the process.

### The phases
Each iteration ("tick") of the loop passes through these phases in order:

```
   ┌───────────────────────────┐
┌─>│         timers            │  setTimeout / setInterval callbacks whose time has passed
│  └─────────────┬─────────────┘
│  ┌─────────────┴─────────────┐
│  │     pending callbacks     │  some system errors deferred from the previous tick
│  └─────────────┬─────────────┘
│  ┌─────────────┴─────────────┐
│  │       idle, prepare       │  internal
│  └─────────────┬─────────────┘
│  ┌─────────────┴─────────────┐
│  │           poll            │  retrieve new I/O events; run I/O callbacks; may block here
│  └─────────────┬─────────────┘
│  ┌─────────────┴─────────────┐
│  │           check           │  setImmediate callbacks
│  └─────────────┬─────────────┘
│  ┌─────────────┴─────────────┐
└──┤      close callbacks      │  e.g. socket.on('close')
   └───────────────────────────┘
```

### Microtasks run between everything
Two queues are drained **after every single callback** (and after the main script), before the loop moves on:

1. The **`process.nextTick` queue** — drained first.
2. The **promise microtask queue** — `.then`/`await` continuations and `queueMicrotask`.

So the order is: current synchronous code → all `nextTick`s → all microtasks → next macrotask (timer, I/O, immediate…).

### setTimeout(0) vs setImmediate
- From the **main module**, their order is **non-deterministic** — it depends on whether 1 ms has elapsed by the time the loop starts.
- From **inside an I/O callback**, `setImmediate` **always** runs first, because the check phase comes right after poll.

### Starvation and blocking
- A recursive `process.nextTick` (or endlessly chained microtasks) **starves** the loop: I/O and timers never get a turn.
- Synchronous CPU work (big `JSON.parse`, sync crypto, `readFileSync`, regex backtracking, tight loops) **blocks** the loop for its duration.

Use `setImmediate` to yield between chunks of long work, or move the work to a worker thread (A6.2).

### Measuring loop health
`perf_hooks.monitorEventLoopDelay()` samples how late the loop is running. Under healthy load the p99 delay should be a few milliseconds; hundreds of milliseconds means something is blocking.

### 2. Deterministic order inside I/O

```js
// io-order.js
import { readFile } from 'node:fs';

readFile(import.meta.filename, () => {
  setTimeout(() => console.log('timeout'), 0);
  setImmediate(() => console.log('immediate'));
});
```

Run it ten times: `for i in $(seq 10); do node io-order.js; done`. `immediate` always wins. Explain using the phase diagram.

### 3. Nested microtasks and nextTick

```js
// nested.js
setTimeout(() => console.log('timeout'), 0);

Promise.resolve().then(() => {
  console.log('promise A');
  process.nextTick(() => console.log('nextTick inside promise'));
  Promise.resolve().then(() => console.log('promise B (queued by A)'));
});

process.nextTick(() => {
  console.log('nextTick');
  Promise.resolve().then(() => console.log('promise C (queued by nextTick)'));
});
```

### 4. Starve the loop

```js
// starve.js
setTimeout(() => console.log('timer fired — loop is free'), 0);

let count = 0;
function spin() {
  if (++count < 1_000_000) process.nextTick(spin);
  else console.log('nextTick chain finished');
}
spin();
```

The timer only fires after a million `nextTick`s. Now change `process.nextTick(spin)` to `setImmediate(spin)` and observe that the timer fires almost immediately.

### 5. Yield during long work

```js
// chunked.js
import { setImmediate as yieldToLoop } from 'node:timers/promises';

const ticker = setInterval(() => process.stdout.write('.'), 10);

function heavy(i) { let x = 0; for (let j = 0; j < 20_000; j++) x += Math.sqrt(i * j); return x; }

// Blocking version
console.time('blocking');
for (let i = 0; i < 2000; i++) heavy(i);
console.timeEnd('blocking');   // no dots printed during this

// Chunked version
console.time('chunked');
for (let i = 0; i < 2000; i++) {
  heavy(i);
  if (i % 100 === 0) await yieldToLoop();   // let timers & I/O run
}
console.timeEnd('chunked');    // dots appear while it runs
clearInterval(ticker);
```

### 6. Measure event loop delay

```js
// lag.js
import { monitorEventLoopDelay } from 'node:perf_hooks';
import { createServer } from 'node:http';

const h = monitorEventLoopDelay({ resolution: 10 });
h.enable();

setInterval(() => {
  const ms = (ns) => (ns / 1e6).toFixed(1);
  console.log(`loop delay p50=${ms(h.percentile(50))}ms p99=${ms(h.percentile(99))}ms max=${ms(h.max)}ms`);
  h.reset();
}, 2000);

createServer((req, res) => {
  if (req.url === '/block') {
    const end = Date.now() + 500;
    while (Date.now() < end) {}          // simulate CPU work
  }
  res.end('ok\n');
}).listen(3000, () => console.log('try: curl localhost:3000/block'));
```

Hit `/block` a few times and watch p99 and max jump to ~500 ms. While one `/block` request runs, a request to `/` also waits.
