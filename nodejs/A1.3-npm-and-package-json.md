## Goal
Manage a Node project's dependencies and scripts confidently, and understand exactly what happens during `npm install`.

## Background

### package.json is the project manifest
It declares the project's name, version, module type, entry points, scripts, and dependencies. The most important fields:

| Field | Meaning |
|-------|---------|
| `type` | `"module"` (ESM) or `"commonjs"` |
| `scripts` | Named commands run with `npm run <name>` |
| `dependencies` | Needed at runtime |
| `devDependencies` | Needed only for development/testing/building |
| `engines` | Supported Node versions |
| `main` / `exports` | What other code gets when it imports this package |
| `bin` | CLI commands this package installs |

### Semantic versioning
Versions are `MAJOR.MINOR.PATCH`. A **major** bump may break your code, a **minor** adds features compatibly, a **patch** fixes bugs. Ranges in `package.json`:

- `^1.4.2` — any `1.x.x` ≥ 1.4.2 (default when you `npm install`)
- `~1.4.2` — any `1.4.x` ≥ 1.4.2
- `1.4.2` — exactly that version

For `0.x` versions, `^0.4.2` only allows `0.4.x` — pre-1.0 minors are treated as breaking.

### The lockfile
`package-lock.json` records the **exact** resolved version and integrity hash of every package in the tree, including transitive dependencies. Commit it. `npm install` may update it within your ranges; `npm ci` installs exactly what it says and fails if it doesn't match `package.json` — use `npm ci` in CI and Docker.

### node_modules and hoisting
npm flattens (hoists) dependencies into the top-level `node_modules` where possible. That means your code can accidentally import a package you never declared ("phantom dependency"). Always declare what you import.

### Scripts and npx
`npm run <script>` runs a command with `./node_modules/.bin` on the `PATH`, so locally installed CLIs work without global installs. `pre<name>` and `post<name>` scripts run automatically around `<name>`. `npx <pkg>` runs a package's binary — downloading it temporarily if it isn't installed.

### Supply-chain hygiene
Every dependency is code you run with full permissions. Prefer few, well-maintained packages; run `npm audit`; review `postinstall` scripts; use `npm ci --ignore-scripts` when you don't need install scripts.

## Tasks

### 1. Create a project and inspect it

```bash
mkdir a1-3-npm && cd a1-3-npm
npm init -y
npm pkg set type=module
npm pkg set engines.node=">=22"
cat package.json
```

### 2. Install runtime and dev dependencies

```bash
npm install picocolors
npm install --save-dev eslint
npm ls            # top-level tree
npm ls --all      # full tree including transitive deps
```

Open `package.json` and `package-lock.json`. Find `picocolors` in both — note the range vs the exact version and `integrity` hash.

### 3. Use a dependency

```js
// index.js
import pc from 'picocolors';

console.log(pc.green('success'), pc.red('error'), pc.bold(pc.cyan('info')));
```

```bash
node index.js
```

### 4. Write scripts

```bash
npm pkg set scripts.start="node index.js"
npm pkg set scripts.dev="node --watch index.js"
npm pkg set scripts.lint="eslint ."
npm pkg set scripts.prestart="echo 'about to start'"
npm start
npm run dev
```

`npm start` runs `prestart` first. `npm run lint` finds `eslint` in `node_modules/.bin` even though it's not installed globally.

### 5. Pass arguments to scripts

```js
// greet.js
console.log('args:', process.argv.slice(2));
```

```bash
npm pkg set scripts.greet="node greet.js"
npm run greet -- --name Ada
```

Everything after `--` is passed to the script.

### 6. Explore semver ranges

```bash
npm view picocolors versions --json | tail -5
npm outdated
npx semver -r "^1.0.0" 1.0.0 1.5.3 2.0.0
npx semver -r "~1.0.0" 1.0.0 1.0.9 1.1.0
npx semver -r "^0.4.2" 0.4.9 0.5.0
```

### 7. Reproducible installs

```bash
rm -rf node_modules
npm ci
npm audit
```

### 8. Inspect a package's install scripts

```bash
npm view eslint scripts
npm explain picocolors
```
